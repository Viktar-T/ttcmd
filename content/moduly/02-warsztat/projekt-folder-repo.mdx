Spróbuj czegoś, co zajmie minutę. Znajdź na dysku pliki, które twój agent
stworzył podczas pierwszego eksperymentu (Zadanie 2.1), oraz kartę obserwacji w swoim
repozytorium.

Zanim zaczniemy budować aplikacje, projekt musi mieć adres — jeden folder i
repozytorium — oraz sprawdzony zestaw narzędzi, którymi się go buduje. Tym
zajmujemy się dzisiaj.

## Jeden folder, jeden projekt

Zasada jest jednozdaniowa: **jeden projekt mieszka w jednym folderze i nie
dzieli go z niczym innym**. Powody są dwa i oba są praktyczne.

Pierwszy dotyczy agenta. Kiedy otwierasz edytor „na folderze”, ten folder jest
dla agenta całym światem: to, co w nim leży, agent widzi, a tego, co poza nim —
nie. Folder, w którym leży pięć niepowiązanych projektów, daje mu pięć razy
więcej do przeczytania i pięć okazji, żeby zmienić nie ten plik, o który
chodziło. Folder z jednym projektem daje dokładnie to, co potrzebne, i nic
poza tym.

Nazwa folderu ma trzy wymagania, wszystkie z tego samego powodu — nazwa folderu
trafia potem do poleceń, do adresu repozytorium i do wielu miejsc, w których
spacja albo ogonek sprawia kłopot:

- małe litery,
- myślnik zamiast spacji,
- bez polskich znaków.

Projekt, który prowadzimy przez resztę tego modułu, nazywa się `pierwsze-okno`.
Utwórz dla niego folder w umówionym miejscu — i na razie nic więcej.

## Git i GitHub: repozytorium od pierwszego dnia

Folder już jest. Drugie zabezpieczenie — repozytorium — zakładamy, zanim
powstanie pierwsza linijka kodu, i za chwilę będzie jasne dlaczego.

**Git** to program, który zapisuje stan projektu w momentach wybranych przez
ciebie i potrafi pokazać różnicę między dowolnymi dwoma z nich. **GitHub** to
serwis, w którym te zapisy leżą także poza twoim komputerem. Programiści używają
ich powszechnie z trzech powodów naraz: praca nie ginie razem ze stanowiskiem,
do wersji, która działała, wraca się poleceniem zamiast odtwarzania z pamięci, a
każdą zmianę można przeczytać, zanim się ją przyjmie.

Trzeci z tych powodów sprowadził Gita akurat do tej lekcji. Od następnych zajęć
spora część zmian w twoim projekcie nie będzie twoja — dopisze je agent. Bez
historii pytanie „co on właściwie zmienił” jest pytaniem do pamięci; z historią
jest pytaniem do jednego polecenia. Na tej różnicy stoi cały ten moduł.

Same polecenia poznaje się w lekcji o Gicie z Modułu 0 i nie tłumaczy się ich
tu od nowa — tu się ich używa. Repozytorium zaczyna się w folderze, który przed
chwilą powstał:

```bash
cd pierwsze-okno
git init
```

`git init` zakłada w folderze ukryty podfolder `.git` i to w nim od tej chwili
mieszka cała historia. Folder jest już repozytorium — na razie pustym.

Napisz `README.md`: jedno zdanie o tym, czym ten projekt będzie. To wystarczy na
pierwszy punkt w historii:

```bash
git add README.md
git commit -m "opisz projekt pierwsze-okno"
```

Teraz kopia poza tym komputerem. Na GitHubie załóż **puste** repozytorium o tej
samej nazwie — `pierwsze-okno` — bez README, bez `.gitignore` i bez licencji;
odznacz wszystko, co GitHub proponuje dołożyć, bo inaczej pierwsze wysłanie
zostanie odrzucone jako niezgodne z tym, co masz u siebie. GitHub pokaże adres
repozytorium; wklej go poniżej w miejsce przykładowego:

```bash
git remote add origin https://github.com/twoja-nazwa/pierwsze-okno.git
git push -u origin main
```

`remote add` zapisuje, dokąd ma trafiać `push`, a `origin` to przyjęta nazwa
tego jednego adresu. Opcja `-u` przy pierwszym wysłaniu wiąże twoją gałąź z
gałęzią na GitHubie, więc od następnego razu wystarczy samo `git push`. Gałąź
nazywa się `main`, bo tak ustawiła ją jednorazowa konfiguracja Gita z Modułu 0.

Sprawdź wynik tak, jak w tym module sprawdza się wszystko — nie założeniem,
tylko poleceniem:

```bash
git status
```

`nothing to commit, working tree clean` znaczy, że u ciebie nie ma nic
niezapisanego. Odśwież teraz stronę repozytorium na GitHubie: `README.md` ma tam
być widoczny. Dwa dowody z dwóch różnych miejsc — i dopiero razem znaczą, że
kopia naprawdę istnieje.

Git jest większy niż te sześć poleceń i w pewnym momencie zaczniesz po niego
sięgać szerzej. Poniżej są cztery miejsca, w których tłumaczy się sam lepiej,
niż zrobiłaby to jedna sekcja. Zajrzyj do każdego na pięć minut i zdecyduj,
które jest twoje — to nie jest lista do przeczytania w całości dzisiaj:

- [Learn Git Branching](https://learngitbranching.js.org/?locale=en_EN) —
  trening w przeglądarce. Wpisujesz polecenie, a rysunek commitów i gałęzi
  przerysowuje się na twoich oczach; repozytorium jest udawane, więc niczego nie
  da się tu zepsuć. Adres z `?locale=pl` na końcu przełącza całość na polski.
- [Pro Git: Installing Git](https://git-scm.com/book/en/v2/Getting-Started-Installing-Git)
  — jeden rozdział o tym, jak zainstalować Gita na Linuksie, macOS i Windowsie.
  Potrzebny wtedy, gdy chcesz pracować nad projektem także w domu.
- [Pro Git](https://git-scm.com/book/en/v2) — cała książka, z której pochodzi
  rozdział wyżej: darmowa i po angielsku, napisana przez Scotta Chacona i Bena
  Strauba. Na ten kurs wystarczą pierwsze trzy rozdziały, a rozdział o historii
  przyda się, kiedy zaczniesz czytać zmiany wprowadzane przez agenta. Polskie
  tłumaczenie jest częściowe i leży pod
  [git-scm.com/book/pl/v2](https://git-scm.com/book/pl/v2).
- [Source control in VS Code](https://code.visualstudio.com/docs/sourcecontrol/overview)
  — te same operacje bez terminala: panel kontroli wersji, wybieranie zmian do
  commita i widok różnicy obok siebie. Cursor wyrósł z VS Code, więc ten panel
  wygląda w nim tak samo.

Pierwsze z nich jest interaktywne i od niego warto zacząć — o nim jest ostatnie
dzisiejsze ćwiczenie.

## SDK — narzędzia, którymi buduje się programy

Zostaje jedna rzecz, i to taka, której nie widać. Kod sam z siebie nie jest
programem; ktoś musi go zamienić w coś, co się uruchamia. Robi to zestaw
narzędzi, który na tym komputerze albo jest, albo go nie ma.

**SDK** (*software development kit*) to komplet narzędzi do budowania programów
w danej technologii: kompilator, podstawowe biblioteki i polecenia, które
uruchamiają jedno i drugie. Nas interesuje **.NET SDK** — zestaw, którym buduje
się programy w języku C#, i ten, na którym stoi reszta tego modułu.

I tu zaczyna się nawyk, na którym cały moduł się opiera: **twierdzenie o
środowisku sprawdza się poleceniem, a nie przyjmuje na wiarę**. „Powinno być
zainstalowane” nie jest odpowiedzią. Odpowiedzią jest to, co wypisze komputer.

Polecenia wpisuje się w **terminalu** — to ta sama konsola, w której uruchamiasz
programy w szkole, tyle że w edytorze z agentem jest zwykle w panelu na dole,
otwartym w folderze projektu. Wpisz w nim:

```bash
dotnet --list-sdks
```

Odpowiedź wygląda mniej więcej tak — u ciebie numery i ścieżka mogą się różnić:

```text
10.0.100 [C:\program files\dotnet\sdk]
```

Pierwsza część to numer wersji, druga — folder, w którym zestaw leży. Wersja,
o którą nam chodzi, zaczyna się od dziesiątki: .NET 10 jest obecnym wydaniem
**LTS**, czyli takim z długim wsparciem. [Zasady wsparcia .NET](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)
mówią, że LTS to trzy lata poprawek od premiery; dla .NET 10, wydanego 11
listopada 2025, oznacza to wsparcie do 14 listopada 2028 — dłużej, niż potrwa
ten kurs, i to jest jedyny powód, dla którego akurat ta wersja nas interesuje.

Jeśli polecenie nie wypisze nic albo odpowie, że nie zna polecenia `dotnet`,
zainstaluj SDK samodzielnie — instalatory dla Windowsa, macOS i Linuksa leżą na
[stronie pobierania .NET 10](https://dotnet.microsoft.com/download/dotnet/10.0).
Po instalacji zamknij terminal, otwórz go na nowo i powtórz polecenie: dopiero
jego wynik jest dowodem, że się udało.

Wynik wklej do `README.md`, pod opis. Za trzy tygodnie, kiedy coś przestanie się
budować, pierwsze pytanie brzmi „a co ja tu właściwie mam zainstalowane” — i ta
jedna linijka na nie odpowie. Zapisz ją w historii:

```bash
git add README.md
git commit -m "zapisz wersje SDK na stanowisku"
git push
```

## Pusty, ale prawdziwy

W folderze, który masz teraz, nie ma ani jednej linijki kodu aplikacji. Jest za
to wszystko, czego brakowało przy pierwszym eksperymencie: adres, pod którym
projekt leży i pod którym zostanie; historia, zaczęta zanim było co
kontrolować; kopia poza tym komputerem; i sprawdzona — nie założona —
odpowiedź na pytanie, czy jest tu czym budować.

- **Nowy projekt zaczynaj od folderu i repozytorium**, nie od pierwszego pliku.
  Odwrotna kolejność kosztuje pół godziny przenoszenia w tygodniu, w którym
  akurat się spieszysz.
- **Edytor otwieraj na folderze projektu**, nie na pulpicie i nie na całym
  dysku. To, co widzisz w drzewku plików, widzi też agent.
- **Każde „powinno działać” zamieniaj na polecenie.** To najtańsza rzecz w całym
  tym module i jedyna, która działa tak samo w trzeciej klasie i w pracy.
- **Wynik sprawdzenia zapisuj tam, gdzie się go potem szuka.** README twojego
  projektu jest takim miejscem; własna pamięć nie jest.

W następnej lekcji folder przestaje być pusty. Stanie w nim okno, postawione
przez gotowy wzór projektu, bez udziału AI — i zmienisz je własną ręką, plik po
pliku. Agent dostanie do zmieniania osobne, drugie repozytorium, żeby dało się
zobaczyć różnicę między jednym a drugim.
