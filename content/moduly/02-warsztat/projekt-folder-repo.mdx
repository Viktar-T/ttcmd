Spróbuj czegoś, co zajmie minutę. Znajdź na dysku folder z Zadania 2.1:
aplikację, którą zbudował twój agent, i kartę obserwacji
`obserwacje/pierwszy-agent.md`.

Zadanie kończyło się zdaniem, że jedno i drugie ma trafić do repozytorium na
GitHubie, zanim wypełnisz formularz. Na razie to jednak tylko pliki: nie mają
historii ani kopii poza tym komputerem, a to, czym się je buduje, nikt jeszcze
nie sprawdził.

Dziś ten sam folder stanie się projektem: z jednym adresem, z historią w Gicie i
kopią na GitHubie, i ze sprawdzonym zestawem narzędzi, którymi się go buduje.

## Jeden folder, jeden projekt

Zasada jest jednozdaniowa: **jeden projekt mieszka w jednym folderze i nie
dzieli go z niczym innym**. Powody są dwa i oba są praktyczne.

Pierwszy dotyczy agenta. Kiedy otwierasz edytor „na folderze”, ten folder jest
dla agenta całym światem: to, co w nim leży, agent widzi, a tego, co poza nim —
nie. Folder, w którym leży pięć niepowiązanych projektów, daje mu pięć razy
więcej do przeczytania i pięć okazji, żeby zmienić nie ten plik, o który
chodziło. Folder z jednym projektem daje dokładnie to, co potrzebne, i nic
poza tym.

Nazwa folderu z Zadania 2.1 powstała według wzoru, który ma trzy wymagania,
wszystkie z tego samego powodu — nazwa folderu trafia potem do poleceń, do
adresu repozytorium i do wielu miejsc, w których spacja albo ogonek sprawia
kłopot:

- małe litery,
- myślnik zamiast spacji,
- bez polskich znaków.

Sprawdź dwie rzeczy, zanim pójdziesz dalej. Po pierwsze nazwę: ma wyglądać tak
jak w zadaniu, na przykład `2.1-stoper-4tc-1-viktar-t`. Po drugie miejsce:
folder ma leżeć w umówionym miejscu na dysku. Jeśli leży gdzie indziej, przenieś
go tam teraz, zanim powstanie w nim repozytorium.

## Git i GitHub: repozytorium od pierwszego dnia

Folder już jest i jest w nim kod. Brakuje drugiego zabezpieczenia —
repozytorium — i za chwilę będzie jasne, dlaczego bez niego trudno pracować z
agentem.

Zanim cokolwiek zainstalujesz, **załóż konto na GitHubie** — w serwisie, w którym
twoje repozytorium będzie miało kopię poza tym komputerem. W tej sekcji konto
przyda się trzy razy: jeśli zechcesz ukryć prywatny adres e-mail w commitach,
przy zakładaniu repozytorium na GitHubie i przy wysyłaniu do niego projektu.
Jeśli konto już masz, przejdź od razu dalej.

Konto zakłada się na stronie [github.com/signup](https://github.com/signup),
odpowiadając na kolejne pytania formularza; na końcu GitHub poprosi o
potwierdzenie adresu e-mail. Tak opisuje to
[dokumentacja GitHuba o zakładaniu konta](https://docs.github.com/en/get-started/start-your-journey/creating-an-account-on-github).
Nazwę użytkownika wybierz z namysłem, bo zobaczy ją każdy: stanie się częścią
adresu każdego twojego repozytorium, tak jak `twoja-nazwa` w adresie
`https://github.com/twoja-nazwa/…` dalej w tej lekcji.

- [Pro Git: Installing Git](https://git-scm.com/book/en/v2/Getting-Started-Installing-Git)
  — jeden rozdział o tym, jak zainstalować Gita na Linuksie, macOS i Windowsie.
  Potrzebny wtedy, gdy chcesz pracować nad projektem także w domu.

Ten rozdział opisuje instalację na trzech systemach naraz. Na Windowsie cała
droga ma trzy kroki: sprawdzić, czy Git już jest, zainstalować go, jeśli go nie
ma, i raz przedstawić się Gitowi. Zacznij od sprawdzenia — w terminalu wpisz:

```bash
git --version
```

Jeśli Git jest zainstalowany, odpowiedź wygląda mniej więcej tak — u ciebie
numer może być inny:

```text
git version 2.51.1.windows.1
```

Wtedy przejdź od razu do konfiguracji niżej. Jeśli terminal odpowie, że nie zna
polecenia `git`, pobierz instalator ze strony
[Git – Install for Windows](https://git-scm.com/install/windows). Wybierz
**Git for Windows/x64 Setup**; wersja **ARM64** jest tylko dla komputerów z
procesorem ARM.

Instalator zadaje po drodze sporo pytań. Prawie wszędzie zostaw to, co jest
zaznaczone, i przechodź dalej — zmień tylko dwa ekrany:

- **Choosing the default editor used by Git** — domyślnie zaznaczony jest
  edytor działający w terminalu, z własnym zestawem skrótów. Wybierz edytor,
  który znasz: **Use Notepad as Git's default editor** albo, jeśli masz VS Code,
  **Use Visual Studio Code as Git's default editor**.
- **Adjusting the name of the initial branch in new repositories** — zaznacz
  **Override the default branch name for new repositories** i wpisz `main`.
  Dalej w tej lekcji gałąź nazywa się właśnie tak.

Po instalacji zamknij terminal, otwórz go na nowo i powtórz `git --version`.
Dopiero ta odpowiedź jest dowodem, że instalacja się udała.

Zostaje konfiguracja, potrzebna na każdym komputerze, także na takim, na którym
Gita instalował ktoś inny. Każdy commit zapisuje, kto go zrobił — imię i
nazwisko oraz adres e-mail — a jak pisze
[Pro Git](https://git-scm.com/book/en/v2/Getting-Started-First-Time-Git-Setup),
te dane zostają w commicie na stałe. Podaj je Gitowi raz:

```bash
git config --global user.name "Imię Nazwisko"
git config --global user.email "twoj-adres@example.com"
git config --global init.defaultBranch main
```

Opcja `--global` znaczy: dla wszystkich repozytoriów na tym koncie Windowsa. Git
zapisuje te ustawienia w pliku `C:\Users\twoje-konto\.gitconfig`, więc nie trzeba
ich powtarzać w każdym projekcie. Trzecia linijka robi to samo co ekran z nazwą
gałęzi w instalatorze — a na komputerze, na którym Gita instalował ktoś inny,
tylko ona ustawi `main`.

Adres z `user.email` zobaczy każdy, kto obejrzy historię twojego repozytorium.
Jeśli nie chcesz pokazywać prywatnego adresu, w ustawieniach konta GitHub, w
części **Emails**, zaznacz **Keep my email addresses private**. GitHub da ci
wtedy adres w postaci `ID+nazwa@users.noreply.github.com` i to jego wpisz w
`user.email` — tak opisuje to
[dokumentacja GitHuba o adresie w commitach](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-email-preferences/setting-your-commit-email-address).
Na koniec sprawdź, co Git zapamiętał:

```bash
git config --global --list
```

Wśród wypisanych wpisów mają być `user.name`, `user.email` i
`init.defaultBranch=main` — a skoro Git wie już, kim jesteś, może zacząć
zapisywać historię.

### Co to jest Git?

**Git** to program, który zapisuje stan projektu w momentach wybranych przez
ciebie i potrafi pokazać różnicę między dowolnymi dwoma z nich. **GitHub** to
serwis, w którym te zapisy leżą także poza twoim komputerem. Programiści używają
ich powszechnie z trzech powodów naraz: praca nie ginie razem ze stanowiskiem,
do wersji, która działała, wraca się poleceniem zamiast odtwarzania z pamięci, a
każdą zmianę można przeczytać, zanim się ją przyjmie.

Trzeci z tych powodów sprowadził Gita akurat do tej lekcji. Całą aplikację w
twoim folderze napisał agent, a od następnych zajęć będzie dopisywał zmiany do
projektów, które już działają. Bez
historii pytanie „co on właściwie zmienił” jest pytaniem do pamięci; z historią
jest pytaniem do jednego polecenia. Na tej różnicy stoi cały ten moduł.

Repozytorium zakłada się w folderze z aplikacją. Wejdź do niego w terminalu —
zamiast przykładowej nazwy wpisz nazwę swojego folderu z Zadania 2.1 — i załóż
repozytorium:

```bash
cd 2.1-stoper-4tc-1-viktar-t
git init
```

`git init` zakłada w folderze ukryty podfolder `.git` i to w nim od tej chwili
mieszka cała historia. Folder jest już repozytorium, choć jeszcze bez ani jednego
zapisu.

Zanim cokolwiek trafi do historii, trzeba ustalić, czego do niej nie brać.
Budowanie i instalowanie bibliotek zostawia w folderze pliki, które powstają na
nowo przy każdym uruchomieniu i których nikt nie pisał: w programie w C# to
foldery `bin/` i `obj/`, a w aplikacji w przeglądarce, do której agent
doinstalował biblioteki przez npm, folder `node_modules/` — tam według
[dokumentacji npm](https://docs.npmjs.com/cli/v11/configuring-npm/folders)
trafiają pobrane pakiety. Do repozytorium takie foldery nie wchodzą. Wypisuje się
je w pliku **`.gitignore`** w głównym folderze repozytorium. Utwórz go w
edytorze i wpisz:

```text title=".gitignore"
bin/
obj/
node_modules/
```

Ukośnik na końcu znaczy, że chodzi o folder, a wzór bez ukośnika na początku
działa na każdym poziomie — także w podfolderze projektu, na przykład w
`Stoper/bin/`, bo tam budowanie w C# kładzie swoje pliki. Tak opisuje to
[dokumentacja `.gitignore`](https://git-scm.com/docs/gitignore). Wpis, który do
twojej aplikacji nie pasuje, niczemu nie szkodzi.

Kolejność ma znaczenie: `.gitignore` nie działa na pliki, które Git już śledzi,
więc zakłada się go przed pierwszym `git add`, a nie po nim. Teraz weź do
commita wszystko i sprawdź, co naprawdę zostało wzięte:

```bash
git add .
git status --short
```

Każdy wiersz z literą `A` to plik, który wejdzie do pierwszego zapisu: twoja
aplikacja, `obserwacje/pierwszy-agent.md` i `.gitignore`. Jeśli na liście jest
cokolwiek z `bin`, `obj` albo `node_modules`, dopisz brakujący folder do
`.gitignore`, a potem cofnij wybór i weź pliki jeszcze raz:

```bash
git reset
git add .
```

Ostrzeżenia w rodzaju `LF will be replaced by CRLF` dotyczą znaków końca linii
i nie zatrzymują polecenia. Kiedy lista jest czysta, zapisz pierwszy punkt w
historii:

```bash
git commit -m "dodaj aplikacje i karte obserwacji z zadania 2.1"
```

Teraz kopia poza tym komputerem. Na GitHubie załóż **puste** repozytorium o tej
samej nazwie co folder — na przykład `2.1-stoper-4tc-1-viktar-t` — bez README,
bez `.gitignore` i bez licencji;
odznacz wszystko, co GitHub proponuje dołożyć, bo inaczej pierwsze wysłanie
zostanie odrzucone jako niezgodne z tym, co masz u siebie. GitHub pokaże adres
repozytorium; wklej go poniżej w miejsce przykładowego:

```bash
git remote add origin https://github.com/twoja-nazwa/2.1-stoper-4tc-1-viktar-t.git
git push -u origin main
```

`remote add` zapisuje, dokąd ma trafiać `push`, a `origin` to przyjęta nazwa
tego jednego adresu. Opcja `-u` przy pierwszym wysłaniu wiąże twoją gałąź z
gałęzią na GitHubie, więc od następnego razu wystarczy samo `git push`. Gałąź
nazywa się `main`, bo tak ustawiło ją `init.defaultBranch` z konfiguracji na
początku tej sekcji.

Sprawdź wynik tak, jak w tym module sprawdza się wszystko — nie założeniem,
tylko poleceniem:

```bash
git status
```

`nothing to commit, working tree clean` znaczy, że u ciebie nie ma nic
niezapisanego. Odśwież teraz stronę repozytorium na GitHubie: mają tam być
aplikacja, folder `obserwacje` i plik `.gitignore`, a nie ma być `bin`, `obj`
ani `node_modules`. Dwa dowody z dwóch różnych miejsc — i dopiero razem znaczą,
że kopia naprawdę istnieje.

To jest repozytorium, o które prosiło *Zadanie 2.1* w lekcji
[Teraz ty: twój pierwszy agent](/moduly/02-warsztat/teraz-ty-pierwszy-agent).
Dopiero teraz wypełnij formularz z tamtego zadania.

### Węcej o Git

Git jest większy niż polecenia z tej lekcji i w pewnym momencie zaczniesz po niego
sięgać szerzej. Poniżej są cztery miejsca, w których tłumaczy się sam lepiej,
niż zrobiłaby to jedna sekcja. Zajrzyj do każdego na pięć minut i zdecyduj,
które jest twoje — to nie jest lista do przeczytania w całości dzisiaj:

- [Learn Git Branching](https://learngitbranching.js.org/?locale=en_EN) —
  trening w przeglądarce. Wpisujesz polecenie, a rysunek commitów i gałęzi
  przerysowuje się na twoich oczach; repozytorium jest udawane, więc niczego nie
  da się tu zepsuć. Adres z `?locale=pl` na końcu przełącza całość na polski.
- [Pro Git: Installing Git](https://git-scm.com/book/en/v2/Getting-Started-Installing-Git)
  — jeden rozdział o tym, jak zainstalować Gita na Linuksie, macOS i Windowsie.
  Potrzebny wtedy, gdy chcesz pracować nad projektem także w domu.
- [Pro Git](https://git-scm.com/book/en/v2) — cała książka, z której pochodzi
  rozdział wyżej: darmowa i po angielsku, napisana przez Scotta Chacona i Bena
  Strauba. Na ten kurs wystarczą pierwsze trzy rozdziały, a rozdział o historii
  przyda się, kiedy zaczniesz czytać zmiany wprowadzane przez agenta. Polskie
  tłumaczenie jest częściowe i leży pod
  [git-scm.com/book/pl/v2](https://git-scm.com/book/pl/v2).
- [Source control in VS Code](https://code.visualstudio.com/docs/sourcecontrol/overview)
  — te same operacje bez terminala: panel kontroli wersji, wybieranie zmian do
  commita i widok różnicy obok siebie. Cursor wyrósł z VS Code, więc ten panel
  wygląda w nim tak samo.

Pierwsze z nich jest interaktywne i od niego warto zacząć — o nim jest ostatnie
dzisiejsze ćwiczenie.

## SDK — narzędzia, którymi buduje się programy

Zostaje jedna rzecz, i to taka, której nie widać. Kod sam z siebie nie jest
programem; ktoś musi go zamienić w coś, co się uruchamia. Robi to zestaw
narzędzi, który na tym komputerze albo jest, albo go nie ma.

**SDK** (*software development kit*) to komplet narzędzi do budowania programów
w danej technologii: kompilator, podstawowe biblioteki i polecenia, które
uruchamiają jedno i drugie. Nas interesuje **.NET SDK** — zestaw, którym buduje
się programy w języku C#, i ten, na którym stoi reszta tego modułu.

I tu zaczyna się nawyk, na którym cały moduł się opiera: **twierdzenie o
środowisku sprawdza się poleceniem, a nie przyjmuje na wiarę**. „Powinno być
zainstalowane” nie jest odpowiedzią. Odpowiedzią jest to, co wypisze komputer.

Polecenia wpisuje się w **terminalu** — to ta sama konsola, w której uruchamiasz
programy w szkole, tyle że w edytorze z agentem jest zwykle w panelu na dole,
otwartym w folderze projektu. Wpisz w nim:

```bash
dotnet --list-sdks
```

Odpowiedź wygląda mniej więcej tak — u ciebie numery i ścieżka mogą się różnić:

```text
10.0.100 [C:\program files\dotnet\sdk]
```

Pierwsza część to numer wersji, druga — folder, w którym zestaw leży. Wersja,
o którą nam chodzi, zaczyna się od dziesiątki: .NET 10 jest obecnym wydaniem
**LTS**, czyli takim z długim wsparciem. [Zasady wsparcia .NET](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)
mówią, że LTS to trzy lata poprawek od premiery; dla .NET 10, wydanego 11
listopada 2025, oznacza to wsparcie do 14 listopada 2028 — dłużej, niż potrwa
ten kurs, i to jest jedyny powód, dla którego akurat ta wersja nas interesuje.

Jeśli polecenie nie wypisze nic albo odpowie, że nie zna polecenia `dotnet`,
zainstaluj SDK samodzielnie — instalatory dla Windowsa, macOS i Linuksa leżą na
[stronie pobierania .NET 10](https://dotnet.microsoft.com/download/dotnet/10.0).
Po instalacji zamknij terminal, otwórz go na nowo i powtórz polecenie: dopiero
jego wynik jest dowodem, że się udało.

Wynik wklej do pliku `README.md` w głównym folderze projektu; jeśli agent go nie
założył, utwórz go i zacznij od jednego zdania, co to za aplikacja. Za trzy
tygodnie, kiedy coś przestanie się
budować, pierwsze pytanie brzmi „a co ja tu właściwie mam zainstalowane” — i ta
jedna linijka na nie odpowie. Zapisz ją w historii:

```bash
git add README.md
git commit -m "zapisz wersje SDK na stanowisku"
git push
```

## Ten sam folder, teraz projekt

W folderze jest to samo, co zostało po Zadaniu 2.1: aplikacja agenta i karta
obserwacji. Przybyło wszystko, czego tam brakowało: adres, pod którym projekt
leży i pod którym zostanie; historia z pierwszym zapisem; `.gitignore`, który
trzyma z dala od niej pliki z budowania; kopia poza tym komputerem; i
sprawdzona — nie założona — odpowiedź na pytanie, czy jest tu czym budować.

- **Nowy projekt zaczynaj od folderu i repozytorium**, nie od pierwszego pliku.
  Dziś repozytorium powstało w folderze, w którym kod już był, i najpierw
  trzeba było ustalić, czego do historii nie brać.
- **Edytor otwieraj na folderze projektu**, nie na pulpicie i nie na całym
  dysku. To, co widzisz w drzewku plików, widzi też agent.
- **Każde „powinno działać” zamieniaj na polecenie.** To najtańsza rzecz w całym
  tym module i jedyna, która działa tak samo w trzeciej klasie i w pracy.
- **Wynik sprawdzenia zapisuj tam, gdzie się go potem szuka.** README twojego
  projektu jest takim miejscem; własna pamięć nie jest.

W następnej lekcji zaczniesz nowy projekt, `pierwsze-okno`, i tym razem od razu
we właściwej kolejności: folder, repozytorium, a dopiero potem okno, postawione
przez gotowy wzór projektu, bez udziału AI — i zmienisz je własną ręką, plik po
pliku. Agent dostanie do zmieniania osobne, drugie repozytorium, żeby dało się
zobaczyć różnicę między jednym a drugim.
